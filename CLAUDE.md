# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page marketing site for VetCare (a veterinary clinic SaaS), in Bulgarian. Static HTML/CSS/JS — no framework, no bundler-driven templating, no backend. All marketing content lives in one `index.html`; the generated parts are the blog (`/blog`), rendered to static HTML from Markdown at build time (see "Blog"), and the legal page (`/legal`), rendered from the VetCare app's own legal texts (see "Legal page").

**All source lives in the `src/` directory — `src/` is the project root.** `index.html`, `assets/`, `package.json`, `sitemap.xml`, `robots.txt`, etc. all live under `src/`, not the repo root. Run every `npm` command from `src/`, and read every path in this document as relative to `src/` unless stated otherwise (e.g. `assets/js/main.js` means `src/assets/js/main.js`).

## Commands

```bash
cd src              # source + package.json live here — run all npm scripts from src/
npm install        # one-time, installs esbuild, sharp and marked
npm run build       # regenerate the blog, the legal page, the icon subset and sitemap.xml, then minify JS + the stylesheets
npm run blog        # regenerate blog/ from content/blog/ only (see "Blog")
npm run legal       # regenerate legal.html from content/legal/ only (see "Legal page")
npm run icons       # regenerate assets/css/icons.css + assets/fonts/*.woff2 only (see "Icon font")
npm run sitemap     # regenerate sitemap.xml only (see "Sitemap")
npm run watch        # re-minify JS and CSS on every save, and re-run the blog or legal build when content/blog/ or content/legal/ changes (scripts/watch.js)
```

The build order matters: `blog` and `legal` run first because `icons` scans the generated pages for `ti ti-*` classes and `sitemap` lists them.

There is no test suite, lint config, or dev server in this repo. `index.html` references the `.min.` files directly, so **run `npm run build` (or keep `npm run watch` running) after editing `main.js` or `styles.css`**, or the live page won't reflect the change. To preview, just open `index.html` in a browser (or serve the directory statically). On a Windows checkout (`core.autocrlf=true`) the build writes LF over the CRLF working copies, so generated files, `main.min.js` included, show as modified after every build with an empty `git diff --stat`: that's line-ending noise, not a change to commit. For phone-width screenshots, don't trust headless Chrome's `--window-size`: it clamps narrow widths, so a "320px" shot is a cropped desktop layout (the header shows the full nav, not the hamburger). Set the viewport through CDP's `Emulation.setDeviceMetricsOverride`, or screenshot an `<iframe>` of the target width.

`npm run watch` can't just be `esbuild --watch` on two entry points at once (the CLI's `--watch` only supports a single `--outfile`), so `scripts/watch.js` sets up two esbuild watch contexts side by side in one Node process instead of relying on shell job control (`&`), which isn't portable between the Windows and POSIX shells contributors may use.

`sharp` is a devDependency but has no npm script — it's invoked ad hoc (`node -e "require('sharp')..."`) for one-off image work (recompressing PNGs, generating `.webp` companions). No image build pipeline exists.

Deploys are manual: `.github/workflows/deploy.prod.yml` runs only on `workflow_dispatch` and ships whatever is on `main`, so anything merged goes live the next time anyone presses the button. A change that has to wait for something outside this repo (e.g. `privacy.html` text describing an app-repo change that hasn't shipped) waits as an unmerged PR, never as merged-but-undeployed.

## Architecture

- `index.html` — the entire page, section by section (hero, problem, how-it-works, benefits, story, waitlist, pricing, demo, FAQ, contact, footer). Sections are HTML comments (`<!-- HERO -->`, etc.) — use these as anchors when navigating.
- `assets/js/main.js` — a single Alpine.js component (`Alpine.data('vetcare', ...)`) bound at `<body x-data="vetcare">`. Almost all interactive state (mobile menu, scroll state, section tracking, FAQ accordion, the three demo/waitlist/contact forms) lives in this one object. `submitDemo`/`submitWait`/`submitContact` validate, then POST (waitlist and contact to Web3Forms, the demo to the app's own API; see "Form submissions" below) and flip a `*Done`/`*Err`/`*Loading` flag based on the result. The one other component is `Alpine.data('vetcareSteps', ...)`, scoped to the how-it-works tab list.
- **Where-am-I state** (`initSectionSpy`): two `IntersectionObserver`s over `main section[id]`, deliberately not one. The first uses `rootMargin: '-<vcBandTop()>px 0px -55%'` to pick the section being *read* → `activeSection`, which drives `.is-active` + `aria-current` on the nav links and the mobile orientation strip (`.vc-crumb`).
  - **That top inset is not a free number — it must equal `html`'s `scroll-padding-top`**, which is where an anchor click parks a section. Start the band any higher and, right after the jump, the *previous* section's bottom edge is still inside it; the topmost match wins, so the nav lights up the section **above** the one that was clicked. It used to be a hardcoded `-88px` while `scroll-padding-top` is `calc(--vc-header-h + --vc-crumb-h + 12px)` = **118px below 900px and 102px below 560px** (only the ≥900px value, 84px, happened to be under 88) — so every nav link and the whole mobile menu highlighted the wrong section, most visibly `#kontakti`, which is last and has no room below it to scroll on and self-correct. `vcBandTop()` now reads the computed value (`getComputedStyle` resolves the `calc()` to px — verified in Chrome at all three breakpoints) and adds 1px, since the band's top edge is exclusive and sub-pixel rounding could otherwise still count the previous section as inside.
  - `rootMargin` is frozen when an `IntersectionObserver` is constructed, so `initSectionSpy` rebuilds the observer on `resize` when the value actually changes — crossing a breakpoint or rotating a phone otherwise keeps the old band.
  - **`pickSection()` inverts its rule at the bottom of the page, and that is load-bearing.** Mid-page the topmost in-band section wins, so a short section can't steal the highlight from the long one still filling the screen. But the *last* section only has its own height plus the footer left to scroll (1153px today), so once the viewport is taller than that it bottoms out with the previous section still in the band — which then holds the highlight forever. That broke `#kontakti` on every window taller than **~1238px** independently of the `rootMargin` issue above. At the bottom there is nothing below left to read, so the last in-band section is the answer. **This makes the last section's height + the footer's height a real constraint** — shrink either and the threshold drops toward common window sizes.
  - The spy observer only fires on intersection *changes*, and the final pixels of a scroll usually aren't one, so the `scroll` handler in `init()` re-runs `pickSection()`. Drop that call and the bottom-of-page rule never gets a chance to apply. The second tracks plain visibility of `#top` and `#demo` → `onScreen`, which is what `showStickyCta` uses to keep the sticky demo button out of the way where it's redundant. `VC_SECTIONS` (top of `main.js`) maps section ids to the Bulgarian labels the strip shows and defines the "n / 9" count — **add a `<section id>` and it must be added there too**, or the strip goes blank on it. `#top` is absent from that list on purpose (the strip is hidden over the hero).
- `assets/css/styles.css` — one file, organized into clearly delimited banner-comment sections (`/* ── Header ── */`, `/* ── Hero ── */`, etc.) mirroring the HTML sections in the same order. Find the right section by matching the HTML comment, then look for the corresponding CSS banner.
- `assets/js/main.min.js`, `assets/css/styles.min.css`, `assets/css/icons.css` + `icons.min.css`, `assets/fonts/tabler-icons-subset.woff2`, `sitemap.xml`, and everything under `blog/`, `legal.html` — all generated. Never hand-edit; `npm run build` overwrites them. They are committed anyway (like the other `.min.` files) so opening `index.html` straight from a checkout works.
- `privacy.html` — standalone Bulgarian GDPR/ЗЗЛД privacy & cookies policy, structurally separate from `index.html` but sharing the same `x-data="vetcare"` Alpine component (so `openConsent()`, header/footer, etc. all work there too). It's the source of truth for the site's legal-entity details (registered company name/address/ЕИК) and for the data-retention figures quoted in §8 — if the PostHog plan or its dashboard retention settings ever change, update §8 to match, since nothing enforces that link automatically. It also says where each form's data goes: the waitlist and contact forms go through Web3Forms (with hCaptcha) to hello@vetcare.bg, while the demo form sends only the email to the app at `app.vetcare.bg`, which creates the demo account. §3, §4, §6 and §7 describe this, and §6 names every service involved (Web3Forms, PostHog, hCaptcha, Hetzner, Cloudflare, Zoho Mail, Sentry), so update them whenever a form's destination or one of those services changes. §8 has no demo-specific retention item yet: one stating the 14-day deletion and a retention period for the app's `DemoDeletionLogs` record waits until the app actually purges those rows (martinbozhilov/VetCare#498). Move „Последна актуализация“ with every substantive change (§14 points readers to it). §13 („Приложението app.vetcare.bg“, `id="prilozhenieto"`) covers the app: the clinic is the controller of what it enters and we are its processor, we are the controller of users' sign-in, security and service data (basis art. 6(1)(f); retention: while the account is active, acceptance records while the clinic uses VetCare plus 5 years, the action journal while the clinic uses VetCare, page visits 90 days, error reports up to 90 days), the recipients link to `/legal#podizpalniteli`, and it describes browser notifications and voice dictation. §1, §2, §8 and §9 point to it. Its retention figures mirror the app's `AuditRetention` settings (page-visit rows purged after 90 days, change rows kept), the 5-year acceptance-record rule (VetCare#496) and Sentry's 90-day maximum for error events; §7's Cloudflare, Sentry and Zoho entries mirror Annex IV's „Къде“ column. When the app's sub-processor list or those settings change, update §7 and §13 in the same PR as the re-sync (see "Legal page"). Nothing enforces these links.
- **The header nav and the footer exist in four copies**: `index.html`, `privacy.html`, `404.html`, and the shared template in `scripts/lib/page-shell.js`, which both `scripts/build-blog.js` (every blog page) and `scripts/build-legal.js` (`legal.html`) use. A link added or renamed in one has to be changed in all four. Nav order is the page's section order, then „Блог“ (a separate page, so after the in-page links and with no section-spy binding in `index.html`), then the demo CTA. The footer's bottom row is: ©, „Поверителност и бисквитки“, „Общи условия“ (`/legal#obshti-usloviya`), „Правна информация“ (`/legal`), then the „Управление на бисквитките“ button; below 960px it stacks (styles.css, next to `.vc-footer-sep`).
- **The social profiles (Facebook, LinkedIn) are linked from seven places**: the `.vc-footer-social` row in all four footer copies (identical markup in each), the „Последвайте ни“ cards in `#kontakti`, the cards in the waitlist success (inside `x-show="waitDone"`), and the `sameAs` of the `Organization` node in `index.html`'s JSON-LD. A changed or added profile means all seven. They are plain links (`target="_blank" rel="noopener"`), never embeds, follow buttons or pixels, which would load third-party scripts and cookies outside the consent gate.
- `404.html` — branded Bulgarian not-found page, same shell as `privacy.html`. **Every URL in it is root-absolute** (`/assets/...`, `/index.html#kontakti`) because nginx serves it for arbitrary nested paths, where relative URLs would break. It is `noindex` (so `gen-sitemap.js` skips it) and has no canonical/OG tags. Wired up via `error_page 404 /404.html;` in `nginx.conf` and listed in the Dockerfile's `COPY` and cache-busting `sed`/`grep` lines, so it must keep the font `preload` line.
- External dependencies loaded via CDN in `<head>`: Alpine.js (`cdn.jsdelivr.net/npm/alpinejs`), Web3Forms' client script, Google Fonts (**Poppins**, weights 400/500/600/700 — `--font-brand` in `styles.css`). No local copies, no package.json entries for these. **The Tabler icon webfont is the exception** — it's self-hosted and subsetted, see "Icon font" below.
- **Poppins has no Cyrillic glyphs** (verified against its `cmap`: `U+0410`, `U+0411`, `U+044F` all map to glyph 0). Since the copy is Bulgarian, almost all visible text actually renders in the next stack entry — `-apple-system` / `Segoe UI` / `Roboto` — so it looks different per OS, and Latin fragments ("VetCare", "VETERINARY SOFTWARE", "AI") mix a second typeface into the same line. Don't treat Poppins as the font the site displays; it styles the Latin bits only. If the brand font is ever revisited, pick one with Cyrillic coverage (Golos Text, Jost and Montserrat all have it) rather than adding more Poppins weights.
- SEO/sharing metadata (OpenGraph, Twitter cards, JSON-LD `@graph` with `WebSite`/`Organization`/`SoftwareApplication`/`FAQPage`) is inline in `<head>`. The four nodes carry absolute `@id`s (`https://vetcare.bg/#website`, `#organization`, `#software`, `#faq`) and point at each other through them: WebSite and SoftwareApplication `publisher` → Organization, FAQPage `isPartOf` → WebSite and `about` → SoftwareApplication. They are absolute because blog articles name the same Organization from other URLs, where a bare `#organization` would resolve to a different entity. `scripts/build-blog.js` builds that id from `SITE` (`ORG_ID`), and the blog build fails if `index.html`'s Organization node doesn't carry it or the block doesn't parse, so change both together. The Organization's `legalName` must match `privacy.html` §1 character for character („…“ quotes). `operatingSystem` is `Web`: VetCare runs in the browser (installable as a PWA) and has no native iOS or Android app. Validate with validator.schema.org. Google's Rich Results Test no longer checks FAQPage, and it flags SoftwareApplication for lacking `aggregateRating`/`review`, which the site has no genuine source for. The FAQ JSON-LD block and the visible FAQ section (`#chesti-vaprosi`) list the same Q&A pairs — keep them in sync if either changes. `og:image`/`twitter:image` and `sitemap.xml`'s `<image:loc>` have drifted from actual files before (referenced a `.webp` that was never committed) — when touching these, verify the referenced file actually exists in `assets/images/`. The sitemap side of that is now enforced (see "Sitemap"); the `og:`/`twitter:` tags are still unguarded.
- **The share image is `assets/images/vetcare-og.jpg`, rendered from `docs/brand/og-image.html`** (the regeneration command is in that file's comment; edit the template, never the JPG). Both `index.html` and `privacy.html` point at it. Keep it a **1200×630 opaque JPG well under 300 KB**: that's Facebook's recommended size (LinkedIn ~1200×627, X crops to 2:1), X documents SVG as unsupported, LinkedIn is unreliable with WebP, transparent backgrounds render inconsistently (black in some dark modes), and WhatsApp silently drops previews over 600 KB. It is the hero's browser mockup (the `app-pacienti.png` screenshot with Rex on its bottom-left corner, which hides the app's signed-in user name and email), so regenerate it whenever that screenshot or the hero mockup changes, and keep `og:image:alt`/`twitter:image:alt` describing it. Platforms cache previews (WhatsApp for weeks), so re-scrape with Facebook's Sharing Debugger / LinkedIn Post Inspector after changing it.

## Form submissions

- The **waitlist and contact** forms send to `hello@vetcare.bg` via [Web3Forms](https://web3forms.com), not a custom backend (there isn't one). All destination/config values — target email, endpoint URL, access key — live in one place: the `VETCARE_CONTACT` object at the top of `assets/js/main.js`. Change delivery settings there, not per-handler. The repo-root `README.md` has a short "Form submissions" summary of this section that drifted once (it kept saying the demo form went through Web3Forms), so change it together with this one.
- The **demo** form is the exception: `submitDemo` POSTs JSON to the VetCare app's own `/api/demo/request` endpoint (which provisions a demo tenant), not to Web3Forms — hence its handling of `409` (demo already exists) and `429` (rate-limited) on top of the generic error path.

### hCaptcha (waitlist + contact only)

- Both Web3Forms forms carry `<div class="h-captcha vc-captcha" data-captcha="true" data-lang="bg">`, rendered off the back of `web3forms/client/script.js`. Zero-config — Web3Forms proxies its own hCaptcha keys, so there is no sitekey/secret in this repo. The demo form has no captcha; it doesn't go through Web3Forms at all.
- **Neither script is in `index.html` — `loadCaptcha()` in `main.js` injects `web3forms/client/script.js` lazily, and everything else follows from that.** Loading hCaptcha on every page view cost three Lighthouse best-practices audits (`deprecations` — its `api.js` uses the deprecated Protected Audience API; `third-party-cookies` — Cloudflare's `__cf_bm`; `inspector-issues` — the same cookies in its iframes), 11 of 26 points, i.e. a category score of **58**. All three are third-party code that can't be fixed from here, so not loading it until it's needed is the only lever. Late injection is safe because that script does its work synchronously at the end of its IIFE (no `DOMContentLoaded`/`readyState` wait) and only needs the `[data-captcha]` elements to already be in the DOM. `loadCaptcha()` caches its promise (rejections included — re-injecting wouldn't retry `api.js`, since the web3forms script bails out early once an hCaptcha tag exists), so one load serves both forms and every call site is idempotent.
- **The trigger is the visitor's first real input gesture** (`VC_CAPTCHA_WAKE_EVENTS` = `wheel`/`touchstart`/`pointerdown`/`keydown`, wired in `initCaptchaWake()`), plus `@focusin` on both forms and an `await loadCaptcha()` in each submit handler as backstops. **Deliberately not the `scroll` event and not an IntersectionObserver**: Lighthouse resizes the viewport to the full page height for its screenshot, which can fire scroll and re-observe elements, and that would drag hCaptcha back into the audited page load — it never dispatches input events. Waiting for the form itself to be touched was tried and looks broken: `.vc-captcha`'s `min-height` reserves 78px from the start (so nothing shifts when the widget lands), and that reserve reads as an empty hole if the widget only appears once the user is already looking at it. One gesture near the top of the page is seconds of reading ahead of the form. **`initCaptchaWake()` only arms itself on a page that has a `[data-vc-captcha]` container** — `privacy.html`, `404.html` and the blog share the Alpine component but have no form, and used to pull in hCaptcha's scripts and Cloudflare cookies on the first scroll anyway.
- **Both forms need the widget because hCaptcha is enabled per access key**, in the Web3Forms dashboard (app.web3forms.com → the form → Block Spam), and the waitlist shares `VETCARE_CONTACT.web3formsAccessKey` with the contact form. Adding a third Web3Forms form without a widget would break it the moment that toggle is on.
- **Widgets are rendered explicitly from `main.js`, not by anyone's auto-render.** `web3forms/client/script.js` does not render anything itself — it stamps its free-plan sitekey onto each `[data-captcha="true"]` element and injects hCaptcha's `api.js`, forwarding `data-lang`/`data-render`/`data-onload` as `?hl`/`?render`/`?onload`. Both containers therefore carry `data-render="explicit"` + `data-onload="vcCaptchaReady"`, and `window.vcCaptchaReady` renders them via `hcaptcha.render()`, keeping the returned widget ids in `VETCARE_CAPTCHA.widgets`. That's what makes the two forms independently controllable — a bare `hcaptcha.reset()`/`execute()` acts on the *first* widget on the page, i.e. the other form's. **Put `data-render`/`data-onload` on every captcha container**: the web3forms script reads them off the last matching element, so omitting them on one makes behaviour depend on DOM order.
- **The waitlist widget is invisible** (`size: 'invisible'`), the contact one is a normal checkbox. A captcha box under a single email field costs more conversions than it's worth, so `submitWait` triggers the challenge with `hcaptcha.execute(id, { async: true })` and hCaptcha only shows a puzzle when it decides one is needed. `.vc-captcha--invisible` positions the container out of flow rather than `display: none`, so hCaptcha still has a laid-out element to render into. The contact widget renders `size: 'compact'` (and gets `.vc-captcha--compact`) when its container is narrower than 279px (303 × 0.92, what the scaled checkbox needs), i.e. viewports ≤ 356px.
- **The token must be sent explicitly.** Web3Forms' own "client side validation" snippet only works for the plain-HTML `POST` method, where the browser encodes `h-captcha-response` with the form. This site submits JSON, so `captchaToken(name)` fetches it (`getResponse` for the checkbox widget, `execute` for the invisible one) and each handler puts it in the payload. Drop that key and Web3Forms rejects the submission as unverified.
- Captcha is resolved **after** the field checks in `submitWait`/`submitContact` — tokens are single-use, so doing it first would make anyone with a typo'd email solve the puzzle twice. For the same reason `resetCaptcha(name)` runs on the error path.
- `data-lang="bg"` is deliberate: without it the widget follows the browser's UI language, which is the same class of bug the forms' `novalidate` handling exists to avoid. Note it ends up as a **page-global** `?hl=` on the api.js URL (the web3forms script reads it off the last matching element), not a per-widget setting.
- hCaptcha's terms require a visible disclosure wherever the widget isn't shown, hence `.vc-captcha-note` under the waitlist form. hCaptcha is also disclosed in `privacy.html` §6 (processors) and §7 (non-EU transfer) — it processes IP/browser/interaction data on every form submit, independently of the analytics consent choice, since it's strictly necessary for security.

### Demo API endpoint (`resolveDemoApi`)

- The endpoint is resolved once at load: `resolveDemoApi()` reads `<meta name="vetcare-demo-api">` in `index.html` and uses its `content` if non-empty; otherwise it falls back to a `window.location.hostname` branch (localhost → `:5500`, `dev.vetcare.bg` → same host, anything else → same-origin `/api/demo/request`).
- That last fallback is only correct for deploys where something proxies `/api` to the app. **Production is not such a deploy** — `vetcare.bg` serves only static files, so an uninjected meta tag means the demo POST hits the site's own nginx and 404s. The meta tag is what makes production work, not the fallback.
- **Don't hardcode a new environment's URL in `main.js`.** The meta tag is the configuration seam, and it's filled at *image build* time: `ARG DEMO_API_URL` in the Dockerfile `sed`s the value into the empty `content=""`, and `.github/workflows/deploy.prod.yml` passes it via `build-args`. The site is static with no runtime env, so this is deliberately build-time — the published image is environment-specific. To point a deploy somewhere else, change `DEMO_API_URL` in the workflow (or `--build-arg` locally), not the JS.
- The Dockerfile step `grep`s for the injected value and fails the build if it isn't found. If you ever reformat that `<meta name="vetcare-demo-api" content="">` line in `index.html` (attribute order, quoting, whitespace), update the `sed` pattern with it — otherwise the build stops rather than silently shipping the empty tag and falling through to the hostname guess.
- Cross-origin is the normal case in production (`vetcare.bg` → `app.vetcare.bg`), so any new origin must also be added to the app's `DemoRequestApi:AllowedOrigins` in `VetCare/src/VetCare.Web/appsettings.json` — the endpoint is `RequireCors`-gated and the browser will block the POST otherwise. That list is in the *other* repo; a website-only change isn't enough.
- Web3Forms was chosen over Zoho Forms (the business's actual mailbox provider) because Zoho Forms has documented CORS restrictions on `fetch()`-based AJAX submission from external origins — there's no way to get a real success/failure signal back without a full-page redirect or a hidden-iframe workaround, which would break the existing inline `*Done` success-panel UX. Don't reintroduce Zoho Forms for this without re-solving that.
- `VETCARE_CONTACT.web3formsAccessKey` now holds a real Web3Forms access key (obtained at web3forms.com, tied to `hello@vetcare.bg`) — forms are live. If it's ever reset to a `REPLACE_WITH...`-style placeholder, submissions will legitimately fail with the Bulgarian error message; that's expected in that state, not a bug to chase.

## Analytics & cookie consent

- PostHog (EU region: `eu.i.posthog.com`) is wired up via the `VETCARE_ANALYTICS` object and `loadPostHog()` at the top of `assets/js/main.js`, gated by `analyticsEnabled()` — which just checks that `VETCARE_ANALYTICS.posthogKey` isn't still the `'REPLACE_WITH_POSTHOG_PROJECT_KEY'` placeholder. Until a real key is pasted in, analytics is a no-op everywhere (including the consent banner, which never shows).
- Consent is **load-gated, not just capture-gated**: the PostHog script tag itself is only injected after the user clicks "Приемам" (`acceptAnalytics()`), never on page load. Declining (`declineAnalytics()`) never loads it. Choice persists in `localStorage['vc-analytics-consent']` (`'accepted'` / `'declined'`), and PostHog inits with `opt_out_capturing_by_default: true` and `maskAllInputs: true` as defense in depth even after loading. Preserve this load-order — don't refactor toward "load PostHog on every page view and opt out client-side," which is a materially weaker consent story and would make the privacy-policy §5 claim ("нищо не се зарежда" on decline) false.
- `openConsent()` re-opens the consent banner on demand (bound to the footer "Управление на бисквитките" button in both `index.html` and `privacy.html`, and to the button in `privacy.html` §10) — this is the GDPR-required "withdraw as easily as you gave" mechanism, so keep it wired to any future entry point that lets a user reconsider consent.
- `acceptAnalytics()` fires `ph.capture('cookie_consent_given', ...)` right after `loadPostHog()` resolves. This exists specifically for GDPR accountability (Art. 5(2)/7(1) — the controller must be able to *demonstrate* consent, not just have the user's browser remember it): `localStorage['vc-analytics-consent']` alone is proof that lives only on the user's device, not something the site owner can produce on request. The PostHog event's server-side timestamp is that record, at zero backend cost (there is no backend). No equivalent event is fired on decline — the point is to be able to prove affirmative consent happened, not to log refusals.
- When verifying events actually arrive in PostHog, check **Activity → Live events** — it's near-real-time. The default **Insights** view is batch-processed and can lag well behind, and looking there first reads as "analytics isn't working" when it actually is.

## Icon font

- Icons are Tabler, but **self-hosted and subsetted**, not loaded from jsDelivr like the other CDN deps. `scripts/subset-icons.js` scans every page `scripts/lib/pages.js` lists (the root `*.html` plus the generated `blog/*.html`) for `ti ti-*` classes and emits `assets/fonts/tabler-icons-subset.woff2` + `assets/css/icons.css` containing only those glyphs. It runs after the blog and legal builds in `npm run build` (blog, legal, icons, sitemap); `npm run icons` runs it alone. Current numbers: **30 glyphs, 831.4 KB → 5.8 KB of woff2 and 227.3 KB → 1.9 KB of CSS.**
- **Add a `ti ti-*` class and you must regenerate**, or it renders as a blank box. The script fails loudly on an icon name that isn't in `@tabler/icons-webfont`, and re-parses its own output to verify every requested glyph actually has outlines, so a silent blank box shouldn't be possible — but only if you run it. The scan is the literal regex `/\bti ti-([a-z0-9-]+)/`, so `ti` must be immediately followed by `ti-<name>` (`class="ti ti-x vc-y"`, never `class="ti vc-y ti-x"`): an icon written the other way is simply never requested, which no check catches, and it renders blank.
- `tabler-icons.ttf` has a **GSUB table that neither harfbuzz nor opentype.js can parse** ("Coverage format must be 1 or 2"), which is why `subset-font` fails outright on it with a misleading "input file is corrupted". `dropTable(source, 'GSUB')` strips it first. GSUB only powers Tabler's optional ligature syntax (`<i class="ti">arrow-right</i>`), which this site doesn't use — it addresses icons by PUA codepoint via `content:`. Don't "simplify" that strip away.
- The icon CSS is a **plain `<link rel="stylesheet">`, deliberately not** the `preload as=style` + `onload` swap the Google Fonts link uses. A font's `@font-face src` isn't discoverable until its stylesheet is applied, so deferring the CSS deferred the font too; combined with Tabler declaring no `font-display` (default `auto` ≈ `block`), icons stayed invisible for the whole load — worst on the hero CTA's `ti-arrow-right`. The woff2 is `preload`ed next to it so both start at parse time. Keep `font-display: block` (not `swap`): the fallback font has nothing to draw for PUA codepoints, so swapping would flash tofu.
- `crossorigin` on the font preload is required **even though the font is same-origin** — fonts are always fetched in CORS mode, and without it the browser downloads the file twice.
- The Dockerfile's cache-busting `sed` versions the woff2 as well as `icons.min.css`: the font's URL appears twice (the `preload` in every page and the `@font-face` in `icons.min.css`) and both get the same `?v=`, so a deploy that adds a glyph can't pair the new CSS with a cached old font. `/assets/` itself is served with `max-age=3600` (`nginx.conf`).

## Sitemap

- `sitemap.xml` is generated by `scripts/gen-sitemap.js` (fourth step of `npm run build`, after the blog, legal and icons; `npm run sitemap` runs it alone) and committed like the other generated files. It used to be hand-maintained and drifted — it claimed `2026-07-30` for both pages long after `index.html` and `privacy.html` had been edited on two different days. **A `<lastmod>` Google can't trust is worse than none**, since it stops trusting the sitemap's freshness signals wholesale rather than ignoring just that field.
- `<lastmod>` comes from git: the last commit that touched the file, or today's date if the file has uncommitted changes (so a build made mid-edit doesn't stamp the previous commit's date). **The two use different clocks** (today in UTC, the commit's date in the committer's local zone via `%cs`), and a GitHub squash merge re-dates the commit, so a sitemap built before committing or merging can be stale afterwards: run `npm run sitemap` again after committing (and after a squash merge) and commit what it changes. The no-git Docker check below can't catch it, since it compares only the page list.
- **Pages are discovered, not listed.** Any `*.html` in `src/` or `src/blog/` (the list is `PAGE_DIRS` in `scripts/lib/pages.js`, which also maps files to their public URLs) is included unless it declares `<meta name="robots" content="noindex">`, so adding a page needs no edit here. `legal.html` takes its `lastmod` from `content/legal/`, like a blog page from its sources: the page is generated, so its own history also moves with the shared template. The one thing worth adding by hand is an `<image:image>` entry, in the `IMAGES` map at the top of the script — and every path in it is checked against the disk, so the drift described under "Architecture" fails the build instead of shipping. Blog articles get their cover as an `<image:image>` automatically.
- **Blog pages take their `lastmod` from their sources, not from themselves.** They are generated, so their own git history moves whenever the template does (a nav link, a class rename) — not a content change. An article uses its `.md` file and cover image; `/blog` uses all of `content/blog/`, since adding, editing or removing any article changes the list. Neither is ever earlier than the date the page shows (`updated`, else `date`, the same value as its JSON-LD `dateModified`; for `/blog` the newest across articles): the first article was committed the day before its `date`, and git alone put its lastmod before its own publication.
- **Without git the script doesn't write, it verifies.** `.dockerignore` drops `.git`, so inside the image build there is no history to read; rather than invent dates it keeps the committed `sitemap.xml` — but fails the build if that file doesn't list exactly the pages being shipped. That is what catches an article committed without re-running `npm run build`: the image build re-renders the blog from Markdown, so the page would go live while missing from the sitemap. Don't "fix" either half by falling back to file mtimes — a CI checkout gives every file the same checkout timestamp, which is exactly the untrustworthy `lastmod` this replaced.
- No `<priority>`/`<changefreq>`: Google ignores both outright.
- **`sitemap.xml` lists `https://vetcare.bg/` (the apex root), and `index.html`'s `<link rel="canonical">` points there too.** From 2026-08-02 that URL returned `401 Basic realm="Restricted Area"` — a deliberate pre-launch lock (a Cloudflare Worker on the route `vetcare.bg/`). As of 2026-11-03 it returns `200`, i.e. the lock is off. If a lock like that is ever reinstated, don't submit the sitemap or request indexing in Search Console while it's on (Google can't fetch a 401 and reports the sitemap as failed — check with `curl -sI https://vetcare.bg/`), and note that a route without a wildcard only matches the bare path `/`: it would lock the home page while `/blog`, `/privacy.html` and all of `www.vetcare.bg` stay public, and the blog's CTA links to `/#demo` would land visitors on the password prompt. Never swap such a lock for `Disallow: /` in `robots.txt`: that survives launch unnoticed, whereas a forgotten password prompt does not.

## Blog

- **Articles are Markdown in `content/blog/<slug>.md`, images in `content/blog/images/`; `scripts/build-blog.js` renders them into `blog/`** (`npm run blog`, first step of `npm run build`): `blog/index.html` (the list, newest first), `blog/<slug>.html` per article, and `blog/images/` (each image copied byte for byte, plus the WebP versions the `<picture>` serves: `<name>.webp` at full size and `<name>-640.webp`/`-800.webp` (plus `-1200`/`-1600` for larger in-text images), picked through `srcset`/`sizes` so phones don't download the desktop file). **Every image URL the blog emits is versioned with `?v=<first 10 hex of the file's SHA-256>`** — the `<img>` fallback, each `srcset` entry, `og:image`/`twitter:image`, the JSON-LD and the sitemap's `<image:loc>` — so `nginx.conf` serves `/blog/images/` with `max-age=31536000, immutable` (a `map` on `$arg_v`; a URL without `?v=` keeps the 1-hour cache). The hash is of the bytes, not a build id, so an unchanged image keeps its URL and its cached copies across deploys, and a replaced one gets a new URL — which also makes Facebook/LinkedIn fetch the new cover on a re-scrape instead of reusing their copy. The JPG's hash is the source file's (it's a byte copy), which is how `gen-sitemap.js` computes the same URL (`versionedImage()` in `lib/blog-posts.js`); WebP hashes may differ between platforms if libwebp's output does, which is harmless because the Docker build regenerates the HTML that references them. The text is in the HTML; nothing about an article needs JavaScript. Adding an article is a new `.md` file plus its cover — no code change — then `npm run build` and commit everything it changed (including `blog/` and `sitemap.xml`).
- **`blog/` is owned by the generator**: any file in it that a run didn't produce is deleted, so a removed article can't linger as a live URL. Never put anything there by hand. The Docker build re-renders it from `content/blog/` (the output is deterministic — no timestamps, no git), which is why `.dockerignore` explicitly keeps `src/content/blog/**` despite its `*.md` rule.
- **Frontmatter is flat `key: value` between `---` lines, not YAML** — parsed and validated in `scripts/lib/blog-posts.js`. Required: `title` (the H1), `slug` (must equal the file name; lowercase Latin, digits, hyphens), `date` (YYYY-MM-DD), `description` (meta description), `image` (`/blog/images/<file>.jpg`), `image_alt`. Optional: `seo_title` (used for `<title>`/`og:title` when the H1 is too long for a search result — warns past 60 characters), `updated` (YYYY-MM-DD, shown on the page and used as `dateModified`; set it for a real revision, not a typo fix), `keyword` (the search phrase the article targets: a note for the author, accepted so drafts that carry it can be dropped in as they are, and never output, since Google ignores `<meta name="keywords">`) and `tags` (1-4 comma-separated topic labels on one line, e.g. `tags: дневници, екип и права`, shown only on the article page as plain labels under the date, not as links; blank means none). The allowed tags are a closed list kept and checked in the marketing repo (`data/tags.md`), so the build checks only their form: lowercase words with single spaces, each tag all Cyrillic `а-я` or all Latin `a-z`, no repeats. Unknown fields, impossible dates, a slug/file-name mismatch and malformed tags fail the build.
- **The cover must be an exactly 1200×630 JPG**, under 600 KB (hard limit: WhatsApp drops previews above it; warns over 300 KB) — it is the article's `og:image`/`twitter:image` and those tags state 1200×630, so the generator refuses anything else rather than resize it. In-text images (`![alt](/blog/images/x.jpg)`) can be any size; their WebP is capped at 2320px wide (2× the 1160px content width). An image alone in its paragraph becomes a `<figure>` whose caption is its title (`![alt](src "caption")`) or else its alt text — hidden from screen readers when it repeats the alt. The build warns about images in `content/blog/images/` that no article uses.
- **An article body must not contain an H1** (`# …`) — the frontmatter title is the page's only H1; sections are `##`/`###`. The build fails on one.
- **No author is shown.** In the JSON-LD (`BlogPosting`) both `author` and `publisher` are the organisation „VetCare“, never a person, and both carry the home page Organization's `@id` (`ORG_ID`), so they are the same entity as the one in `index.html`'s JSON-LD.
- **URLs are `/blog` and `/blog/<slug>`, no extension and no trailing slash**, and that spelling is what the canonical tags, `og:url`, JSON-LD and `sitemap.xml` use. `nginx.conf` serves `blog/<slug>.html` at it and 301s every other spelling (`.html`, trailing slash, `/blog/index.html`) there; `absolute_redirect off` keeps those redirects relative, because this container only sees HTTP from the front nginx. Opening `blog/*.html` from `file://` doesn't work (every URL in them is root-absolute, like `404.html`) — preview through a server: `npm run serve` serves the same clean URLs (it doesn't redirect `/blog/` to `/blog`, which nginx does).
- The page shell (head tags, header, footer, consent banner) is the shared template in `scripts/lib/page-shell.js` (also used by `/legal`), mirroring `privacy.html`. The styles are the `/* ── Blog ── */` block in `styles.css`: `.vc-blog-*` for the list, `.vc-article-*` for the article frame, and `.vc-prose` for the Markdown output, which has no classes and so is styled by bare element selectors. Both blog pages sit in `.vc-container` (1160px, the index sections' width) with the index sections' side padding, so the content edge stays aligned with the header's logo from page to page. Don't give the blog its own narrower column: 680px (~70 characters a line) and 960px were both tried and rejected — the text didn't fill the page, and the content edge jumped when moving between pages.
- The call to action at the end of every article („Пробвайте демото“ → `/#demo`) is part of the template, not the Markdown, so it is the same everywhere and changes in one place. Blog pages run `main.js` like the rest of the site — the analytics consent banner and PostHog (after consent) included — and nothing else: no share buttons, no comments, no other third-party scripts.

## Legal page

- **`/legal` („Правна информация“) is `legal.html`, generated by `scripts/build-legal.js`** (`npm run legal`, second step of `npm run build`) from the VetCare app's own legal texts: the terms of use, then the data processing agreement (its introduction, the Commission's standard contractual clauses with the parties' choices applied, and Annexes I-IV, Annex IV being the sub-processor list), then „Стари версии“. Like `blog/`, it is generated and committed: never edit it by hand. Every URL in it is root-absolute, so preview it through `npm run serve`, not `file://`.
- **The texts are the app's, copied byte for byte into `content/legal/` and never edited here**: `terms-vN.md`, `dpa-vN.md`, `dpa-vN-clauses.md`, `sub-processors-vN.md` and the manifest `legal-documents.json`, all from `src/MedicalHistory/Legal/Documents/` in the app repo. A published text never changes in the app (a correction is a new version), so the site never "fixes" one, not even for the dash rule. `.gitattributes` keeps them LF, as the app does.
- **The build checks the copy against the manifest.** `scripts/lib/legal-texts.js` hashes each text the way the app's `LegalTextHash.OfText` does (UTF-8, leading BOMs dropped, every line ending turned into LF, SHA-256, lowercase hex) and fails on a mismatch. A mismatch means the copy is wrong, never that the manifest needs another hash.
- **Re-syncing an app release** (a new version, a new sub-processor list, or the real effective date replacing a placeholder) is a copy and a build. In Git Bash, not PowerShell, whose `>` re-encodes the bytes: `for f in terms-v1.md dpa-v1.md dpa-v1-clauses.md sub-processors-v1.md legal-documents.json; do git -C ../VetCare show <commit>:src/MedicalHistory/Legal/Documents/$f > src/content/legal/$f; done`, then `npm run build` from `src/`. `git hash-object src/content/legal/<file>` must equal `git -C ../VetCare rev-parse <commit>:src/MedicalHistory/Legal/Documents/<file>`. The PR names `<commit>` and the four hashes, and is merged and deployed only once the app release carrying the same texts is live (see "Deploys are manual").
- **Rendering follows the app's grammar** (`LegalMarkdownParser.cs`, which reads the files with Markdig: pipe tables and definition lists on, every unmapped construct refused). `scripts/lib/legal-markdown.js` reads the texts with markdown-it (the `commonmark` preset, tables on, `markdown-it-deflist`) and maps the tokens through an allow-list, as `LegalMarkdownParser.cs` maps Markdig's tree, so it accepts a strict subset and refuses everything else with file and line, rather than render a construct differently from the app. A few raw-line checks on the source exist because markdown-it-deflist (Pandoc syntax) and markdown-it's tables accept forms that Markdig (PHP Markdown Extra syntax) refuses or reads differently (a label after a line of text, a lazy continuation, a third level, a ragged table row, edge no-break spaces). Accepted: headings `#`-`#####` (shown as `h2`-`h6` under the page's `h1`), one paragraph per line, `- ` bullet items of one line, pipe tables with one header row, labelled items (the label alone on a line, then `:   ` and the content, nested items four spaces in, two levels at most), `*`/`**`/`***` emphasis, the tokens, the `{{#contact}}`/`{{#acceptance}}` sections and the two includes. If a new app text fails here, extend the parser to match the app; never edit the text.
- **Composition mirrors `LegalDocumentLibrary`.** Tokens are filled after parsing: `{{version}}` from the manifest, `{{effectiveDate}}` and `{{lastChanged}}` as the app prints them on its server (bg-BG short date, `9.11.2026` + a NARROW NO-BREAK SPACE U+202F + `г.`, exactly what the app prints: not an ordinary space, which looks the same; `formatBgDate()`, and the build fails unless every date-shaped text on the page, `<d>.<MM>.<yyyy>` in any form, is exactly that, and there are as many of them as date tokens filled during composition), never hardcoded. `{{> clauses}}` and `{{> sub-processors}}` are expanded in place. The page has no clinic, so Annex I keeps „Администратор(и): …“ and the whole „Обработващ“ block and drops the four clinic lines: the bullet items using `{{clinic.name}}`/`{{clinic.address}}` and the `{{#contact}}`/`{{#acceptance}}` sections.
- **The build proves the page says what the app says.** `scripts/lib/legal-parity.js` cuts the composed source (syntax stripped, tokens filled, includes in place, the Annex I clinic lines dropped) into blocks, one per line, list item, table cell, label and labelled-item content, and compares them one for one, in reading order, with the rendered block elements (`h2`-`h6`, `p`, `li`, `th`, `td`, the label span). Two paragraphs merged into one, a block lost or added, a changed word or a lost or added bold/italic fail the build: `<strong>`/`<em>` are mapped back to `**`/`*` and compared with the source's own markers. Whitespace and no-break spaces are collapsed for the terms and the DPA; the Commission's clauses are compared again with no-break spaces kept, so their two em dashes, 47 no-break spaces and the official typo „даннии“ are proven, not assumed. On top of that, the whole visible text of each region (terms, DPA, clauses), in reading order, must equal the composed source text with the emphasis markers stripped (whitespace collapsed for the terms and the DPA, no-break spaces kept for the clauses), so text outside the block elements (an extra `<div>`, a bare text node, a paragraph repeated inside another element, words after a label) fails too. It does not check which tag a block uses (`h3` against `h4`, `p` against `li`) or which column a cell is in. It also fails on leaked syntax (`{{`, `*`, text starting with `:` or `#`, `|---`) and on a missing or repeated anchor.
- **Only the app's own three texts get the site's treatment**: `glueDash()` before every " - ", and clickable URLs and emails (the words unchanged). The clauses go through `esc()` and nothing else. The dash check covers the page's own copy (title, intro, table of contents, „Стари версии“). The site's copy on the page must never paraphrase an obligation.
- **Annex IV is a real `<table>`** (the header once, the rows in source order, which is what the parity check reads). Below 720px each row becomes a card, with the column names as CSS labels (`data-label` and `content: attr(data-label) / ""`, so screen readers, which keep the table semantics through the explicit ARIA roles, don't hear them twice). The app's screen uses markup records instead; its PDF keeps the table.
- **The anchors are an interface**: `#obshti-usloviya` (the footer's „Общи условия“), `#dogovor-za-obrabotvane`, `#podizpalniteli` (the table of contents and `privacy.html` §13) and `#stari-versii`. Rename one and grep the four footer copies and `privacy.html`.
- **One release, for now.** The build refuses a `legal-documents.json` with more than one release, or with a field it doesn't know, because what the site should show then has not been built. A second release cannot exist before VetCare#495 (the app's build blocks it). From then on:
  - each app release gets its own site PR, with the same version numbers and dates;
  - the current version is the one in effect (its effective date, 00:00 Europe/Sofia, has passed), as in the app;
  - a replaced version moves to „Стари версии“ with its number and „в сила от“ date, and its full text stays readable;
  - a sub-processor change must be followable on the site 14 days ahead (terms 10.2, clause 7.7): an upcoming list with its effective date, from the day the app's notices go out. Deploys are manual, so the switch on the day is a deploy; the mechanism is decided with #495, and so is which list an old DPA version shows (the app always shows the list in effect).
- **Serving**: `nginx.conf` serves `legal.html` at `/legal` (`no-cache`) and 301s `/legal.html` and `/legal/` there; `scripts/lib/pages.js` maps it to `https://vetcare.bg/legal`; `sitemap.xml` takes its `lastmod` from `content/legal/`; the Dockerfile copies and cache-busts it with the other pages, so it keeps the font `preload` line from the shared head; `.dockerignore` keeps `src/content/legal/**`, since the image build renders the page again.

## Images

- No automated image pipeline. When adding/replacing a large raster photo (not an icon), manually: recompress with `sharp` (`png({ compressionLevel: 9, effort: 10, adaptiveFiltering: true })` — lossless, no `palette: true` quantization, which barely shrinks photographic/alpha images further but risks banding), generate a `.webp` companion (`webp({ quality: 85 })` is a good default), and serve both via `<picture><source type="image/webp" srcset="...webp">` + `<img src="....png">` fallback (see the STORY section's `rex-kolaj` image for the pattern).
- Keep an `<img>`'s `width`/`height` attributes equal to the file's real intrinsic pixel dimensions (not a placeholder/aspirational size) — CSS elsewhere uses `width:100%;height:auto`, so these attributes only set the reserved aspect ratio; a mismatch causes layout shift on load.
- On Windows, `convert` on PATH resolves to the OS's built-in disk-conversion utility, not ImageMagick — don't use it for image work.

## Conventions

- **No inline styles.** All CSS goes in `styles.css` under a `vc-` prefixed class — never add `style=""` attributes in HTML. The one accepted exception already in use is `style="display:none"` paired with `x-show`, which exists purely as a pre-hydration flash guard for Alpine (so the element is hidden before Alpine initializes); don't use inline `style` for anything else, including new instances of this pattern if a CSS-class-based alternative is reasonable. The rule is about *static* `style=""` attributes: Alpine's `:style` binding is a different thing and is used once, for the scroll-progress `scaleX()` on `.vc-crumb-progress-fill`, where the value is a continuously changing number that no class can express.
- **Hover vs. press.** Interaction states live in the `/* ── Interaction states ── */` block near the end of `styles.css`, not scattered across each component. Hover rules go inside `@media (hover: hover) and (pointer: fine)` so a tap on a phone doesn't leave an element stuck in its hover state; `:active` rules stay outside it, since that's the press feedback touch depends on.
- Class names are BEM-ish and consistently `vc-*` (e.g. `vc-hero-section`, `vc-mock-appt--dashed`). Match this prefix and the modifier-suffix (`--variant`) style for anything new.
- Alpine directives (`x-show`, `x-model`, `@click`, `:class`) are used throughout instead of vanilla JS DOM manipulation — extend behavior through the `vetcare` Alpine component in `main.js`, not by adding separate `<script>` blocks or querySelector-based JS.
- Copy is in Bulgarian (`lang="bg"`); keep new user-facing text in Bulgarian and consistent in tone with existing copy.
- **No long dashes in anything a visitor reads** — no em dash (—) or en dash (–) in copy, `<title>`, meta/OG text, JSON-LD or blog articles, even when a brief or pasted text has them. Use a hyphen with spaces (" - "), with `&nbsp;` before it where a line wrap would otherwise start a line with the dash. The blog build enforces this (articles and its own templates) and adds the `&nbsp;` itself: in an article's visible text (body, H1, list card) the space before every " - " becomes a no-break space (`glueDash()` in `scripts/lib/page-shell.js`), so authors just type " - ". The hand-written pages are not checked. Code comments are not copy. The legal build checks its own copy too, but never the vendored texts: the Commission's clauses keep their two em dashes (they are a quote), and a long dash in one of the app's other texts only warns, since the app owns the wording.
